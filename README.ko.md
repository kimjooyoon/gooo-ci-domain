# Gooo로 검증 작업을 계획하기

수정이 한 줄이어도 그 값을 여러 패키지가 사용하면 검증량은 커집니다. 이 도구는 변경 파일에서 출발해 영향을 받는 코드와 테스트를 찾고, 관찰한 비용으로 실행 계획을 만듭니다.

Gooo가 **허용 조건, 비용 여유분, 첫 관찰의 조건, 실행 결과, 다음 행동**을 정의합니다. Go는 파일과 import 관계를 읽고, 그래프를 계산하고, 프로세스를 실행합니다. 현재 정책은 [policy.gooo](policy.gooo)에 있으며 실제 Gooo 컴파일러가 생성한 Go 코드와 출처 기록을 함께 공개합니다.

## 동작 흐름

1. 현재 Git 소스와 테스트 import, embed 입력을 관찰합니다.
2. 변경의 영향을 따라 필요한 패키지 테스트를 구성합니다. 소유자를 확인하지 못한 입력은 전체 패키지로 연결합니다.
3. 같은 명령·환경·자원 조건의 기록으로 작업 시간을 예측합니다. 순차 작업과 병렬 자원의 한계도 표시합니다.
4. 처음 보는 기능 수정에는 같은 3분 한도 안에서 필요한 테스트 전체를 관찰합니다. 예측이 없었다는 상태를 그대로 남깁니다.
5. 다음 기능 수정에는 그 비용을 사용합니다. 실패와 시간 초과가 다음 예측과 행동에 반영됩니다.

실행 전에 시작 출처를 저장합니다. 실행이 중단되거나 결과 저장이 실패해도 같은 소스를 자동으로 다시 돌리지 않습니다. 관찰 기록은 소스 폴더 바깥에 보관하며 기본 저널의 용량은 4 MiB로 제한됩니다. 모델 다운로드나 생성형 서비스 없이 사용할 수 있습니다.

```sh
gooo-ci-domain plan --root /path/to/repository --base BASE_COMMIT
gooo-ci-domain improve --root /path/to/repository --base BASE_COMMIT
```

설치는 [영문 안내](README.md#use)에 있습니다. 비용을 사람이 넣는 절차는 기본 흐름에 없습니다.

## 현재 확인한 범위

실제 컴파일러 소스의 두 리비전을 읽었을 때 765개 변경 입력 중 671개는 개별 소비자를 확인하지 못했습니다. 따라서 431개 패키지 전체가 필요한 것으로 판단했고, 예상 비용은 미확정으로 남겼습니다. 이 관찰에서 테스트를 실행한 횟수는 0입니다.

새 입력으로 수행한 작은 실험에서는 첫 실행의 비용 관찰이 다음 기능 수정의 예측에 연결됐습니다. 테스트가 읽은 `.gooo` 파일의 출처도 기록했습니다. 큰 저장소에서의 예측 신뢰도는 계속 관찰해야 합니다.

현재 수집 범위는 **한 호스트 Go 모듈의 추적된 소스 변경과 패키지 테스트**입니다. 컴파일러의 여섯 정식 검사와 외부 도구에는 별도 실행 의무가 있습니다. 전체 컴파일러 CI의 3분 한도는 이 의무까지 연결하는 후속 작업입니다.

GitHub 워크플로에는 3분 작업 한도를 설정했고, 첫 실행기 단계에서 수락한 시각부터 checkout·설치·컴파일·검증이 같은 예산을 사용합니다. GitHub의 원본 실행 JSON과 작업 수락 시각을 함께 보관해 초기 대기도 따로 확인할 수 있습니다. 대기·검증·전송을 합친 전체 완료 시간에는 외부 조건이 함께 작용합니다. [도메인 분석](docs/domain.md)에 이 경계를 정리했습니다.

## 실제 명령 연결

이제 `work`로 format·vet·race·정책 같은 실제 명령을 같은 시계에 연결할 수 있습니다. 커밋, 추적된 작업 파일, 실행 파일의 내용, 명령 인자, 환경을 출처로 묶습니다. 각 단계의 완료와 전체 검증의 완료는 각각 기록해야 합니다. [명령 출처 계약](docs/command-origins.md)에 사용법과 관찰 범위를 정리했습니다.

새 입력 실험에서 동시 호출 두 개 중 한 개만 실행됐고, 작업 파일이나 실행 파일이 바뀌면 출처와 비용 문맥도 달라졌습니다. 기존 소스의 실험을 다시 돌리지 않고 새 기능 입력으로 확인한 결과입니다.
